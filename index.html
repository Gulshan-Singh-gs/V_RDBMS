02 · Storage Models

Relational vs. Non-Relational (NoSQL)

Relational (RDBMS)

Constrained, hard-coded schemas · strict ACID compliance

  • Billing & Subscriptions: memberships, credit-card transactions, invoicing history, financial ledgers.
  • Account Management: credential mappings; constraints prevent orphan records & inconsistent profiles.
  • Reserved for data needing absolute structural integrity.
MySQLPostgreSQL

Non-Relational (NoSQL)

Flexible, unconstrained schemas · real-time scale

  • Viewing History & Resume Playback: second-by-second, write-heavy tracking at millions of concurrency.
  • Recommendation Engine: dynamic metadata, preferences, real-time interaction logs — no fixed schema.
  • Optimized for high-velocity reads/writes.
Apache CassandraAmazon DynamoDBEVCache / Redis

03 · The Dilemma

Why Netflix Avoids Pure Relational for Streaming

Storing all streaming telemetry, user logs and recommendation state in a monolithic RDBMS hits severe bottlenecks.

01 Rigid Schema Constraints

Schema evolution at petabyte scale

  • Personalization metrics evolve constantly.
  • Altering relational tables across petabytes causes massive downtime.
  • NoSQL provides the schema flexibility required.

02 Write Bottlenecks

Locking vs. peak-hour concurrency

  • RDBMS enforces strict locking to keep tables consistent.
  • Peak evening: millions of concurrent "Continue Watching" timestamp writes.
  • A relational engine would choke under the load.

03 Horizontal Scalability

Scale-out on distributed clusters

  • NoSQL is purpose-built to scale out horizontally.
  • Matches Netflix's global cloud infrastructure.
  • Running primarily on AWS.
Professor's note: "A large retail process processes numerous transactions per second against a single account. Why relational, not non-relational?" — For Netflix's streaming data layer, the opposite holds true.

04 · Transactional Core

ACID Properties in Core Systems

NoSQL handles high-speed streaming metadata — but billing & accounts still demand strict ACID guarantees.

Atomicity

The "all-or-nothing" rule

  • A subscription update or monthly payment fully succeeds or rolls back entirely. Partial updates are unacceptable.

Consistency

Valid state, everywhere

  • Account status (active vs. canceled) is instantly reflected across billing and access-control layers.

Isolation

Concurrent, conflict-free

  • Simultaneous multi-device updates — a password change while another profile streams — never corrupt transactional state.

Durability

Committed means permanent

  • Once a payment or account modification is committed, it survives system crashes and server failures.

05 · Conclusion

Conclusion & Key Takeaways

The Power of Multiple Databases

  • Modern enterprise architecture rarely relies on "one-size-fits-all" — it's a multi-database approach.
  • RDBMS for strict, ACID-compliant financial & account transactions.
  • NoSQL for flexible, real-time streaming data at global scale.
  • Outcome: optimal performance, high availability, global scale.
